# Feature structure

How a business domain is laid out in `apps/web/src/features/`, and the rules
that keep the folder navigable.

Each subfolder is one business domain, named after the matching backend module
at `apps/api/src/modules/<domain>/`. The structure is parallel to the backend
so a screen traces back quickly: see `features/taxonomy/` and you know the
domain lives at `apps/api/src/modules/taxonomy/`.

## Folder boundaries

```text
apps/web/src/
  app/                      Next.js owns this tree
    <segment>/_components/  Only used by that segment
  components/
    ui/                     Shared primitives — know nothing about a domain
    providers/              App-wide client providers
  features/
    <domain>/               One folder per business domain
      index.ts              Barrel — the only import surface
      types.ts              Domain types the UI consumes
      hooks/                API calls and state normalisation
      components/           Domain components
      schemas/              zod schemas for the domain's forms
  lib/
    api/                    GENERATED BY Orval — never hand-edited
    axios-instance.ts       Orval mutator — unwraps the response envelope
    api-error.ts            Helpers for reading a failed request
  theme/                    MUI theme
  utils/                    Shared utility functions (date/time formatting, …)
```

## The five rules

> **Four of the five are enforced by eslint**, in
> `apps/web/eslint-rules/researchos-boundaries.mjs`. A convention that only
> lives in prose does not fail a build, so a rule a reviewer has to remember
> is a rule that eventually gets broken. The table below says which are
> enforced and which are not.

| # | Rule | Enforced by |
| --- | --- | --- |
| 1 | `src/lib/api/` is Orval's | `no-restricted-imports` (eslint core) |
| 2 | `components/ui/` knows nothing about a domain | `researchos/no-domain-entities-in-ui` |
| 3 | Features do not import each other | `researchos/no-cross-feature-imports` |
| 4 | The feature folder name matches the backend module | `researchos/feature-name-matches-backend-module` |
| 5 | `src/utils/` holds shared utility functions | convention only |

### 1. The generated API tree belongs to Orval

The config runs with `clean: true`, so every hand-written file there is
deleted on the next codegen. The eslint rule `no-restricted-imports` blocks
**value** imports from `@/lib/api/*` — import values from the `@/lib/api`
barrel instead.

The one exception is a **type-only** import, which the rule permits via
`allowTypeImports`:

```typescript
import type { ApiErrorResponseDto } from '@/lib/api/models';
```

A type is erased at build time, so it cannot pull a deleted runtime module
into the bundle — which is the actual risk the rule guards against.
Importing a *value* from `@/lib/api/*` is still an error.

There are two generated barrels and they export **disjoint** sets:
`@/lib/api` holds the operations (hooks, API functions), while
`@/lib/api/models` holds the types. Neither re-exports the other, so a
type-only import has to name the models barrel explicitly.

Allowed and blocked import forms: [tooling.md](tooling.md#orval-imports).

### 2. `components/ui/` knows nothing about a domain

A file there must not mention `Profile`, `Opportunity` or `Taxonomy`. Same
principle as `src/common/` in the backend. The
`researchos/no-domain-entities-in-ui` rule enforces this — it matches the
entity name in an import binding, an export name, a type reference, or JSX
text.

### 3. Features do not import each other

If a feature needs another feature's data, call that feature's hook, not its
files. The `researchos/no-cross-feature-imports` rule enforces this.

### 4. The feature folder name matches the backend module

`features/taxonomy/` ↔ `apps/api/src/modules/taxonomy/`. This is how a
reviewer traces a screen back to its backend module. The
`researchos/feature-name-matches-backend-module` rule enforces this — it reads
the backend module list from disk.

### 5. `src/utils/` holds shared utility functions

Date/time formatting, string helpers, and so on. A helper used by two
features lives here rather than being duplicated, or buried in one feature's
`hooks/` where the other feature cannot reach it.

## Transport → domain → UI

Three layers, and the middle one exists for a reason.

| Layer | Location | Owns |
| --- | --- | --- |
| Transport | `src/lib/api/` (Orval) | Request, cache key, query lifecycle |
| Domain | `features/<domain>/hooks/` | DTO → domain type, state normalisation |
| UI | `features/<domain>/components/`, `components/ui/` | Rendering |

The domain layer means a screen never branches on raw query flags. It reads
one explicit status.

The `isPending` trap and the flag semantics:
[data-and-errors.md](data-and-errors.md#query-state-cheat-sheet).

## The feature folder

```text
apps/web/src/features/profiles/
  index.ts
  types.ts
  hooks/
    use-profile.ts
    use-profiles.ts
  components/
    profile-card.tsx
```

A feature folder is `index.ts` (barrel), `types.ts` (domain types), `hooks/`
(API calls + state normalisation) and `components/`.

Do not create a feature folder before the domain exists — `health/` was the
first one.

### `index.ts`

```typescript
/**
 * Profiles feature — public entry point.
 *
 * This barrel is the only import surface other modules should use.
 */

export { useProfile } from './hooks/use-profile';
export { useProfiles } from './hooks/use-profiles';
export type { Profile } from './types';
```

### `types.ts`

```typescript
/**
 * Domain types for the profiles feature.
 *
 * Derived from the generated API models but kept separate, so a backend field
 * rename surfaces here first.
 */

export interface Profile {
  id: string;
  displayName: string;
  createdAt: string;
}
```

### `hooks/use-profiles.ts` — list

```typescript
'use client';

import { useProfilesControllerFindAll } from '@/lib/api';
import type { Profile } from '../types';

export function useProfiles() {
  const query = useProfilesControllerFindAll();

  const data: Profile[] | undefined = query.data
    ? query.data.map((item) => ({
        id: item.id,
        displayName: item.displayName,
        createdAt: item.createdAt,
      }))
    : undefined;

  return {
    ...query,
    data,
    isLoaded: query.isSuccess,
    isFetching: query.isFetching,
    isFailed: query.isError,
  };
}
```

### `hooks/use-profile.ts` — detail

```typescript
'use client';

import { useProfilesControllerFindOne } from '@/lib/api';
import type { Profile } from '../types';

export function useProfile(id: string) {
  const query = useProfilesControllerFindOne(id, {
    query: { enabled: Boolean(id) },
  });

  const data: Profile | undefined = query.data
    ? {
        id: query.data.id,
        displayName: query.data.displayName,
        createdAt: query.data.createdAt,
      }
    : undefined;

  return {
    ...query,
    data,
    isLoaded: query.isSuccess && data !== undefined,
    isFetching: query.isFetching,
    isFailed: query.isError,
  };
}
```

The hook is where the DTO becomes a domain type, and where raw query flags
become explicit ones. Note `enabled: Boolean(id)` — without it, a request
fires with an empty id.

The component then branches on the hook's explicit flags, never on
`query.data` being undefined — an `isPending` branch renders a
`LoadingSkeleton`, an `isFailed` branch renders an `ErrorState` with a
retry, and only then does it read `data`.

## Forms

Forms use react-hook-form + zod + the MUI form components. The full rules
live in the `researchos-forms` skill, and eslint enforces them in
`apps/web/eslint-rules/researchos-forms.mjs`:

| Rule | Fails when |
| --- | --- |
| `researchosForms/no-native-form-controls` | `<input>` / `<select>` / `<textarea>` instead of a MUI component (except `input type="hidden"`) |
| `researchosForms/form-must-use-react-hook-form` | A `<form>` in a file that does not import `useForm` |
| `researchosForms/form-must-handle-submit` | A `<form>` without `onSubmit` |
| `researchosForms/form-control-must-be-wired` | A MUI control not bound into the form |
| `researchosForms/select-requires-controller` | `<TextField select>` using `register()` instead of `Controller` |
| `researchosForms/form-error-must-be-resolved` | An error message rendered raw instead of resolved through the catalog |

Reusable controls: `FormTextField`, `FormSelect`, `FormCheckbox` in
`src/components/ui/form.tsx` — they bind into the form and resolve the error
message themselves.
