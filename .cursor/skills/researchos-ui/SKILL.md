# ResearchOS UI

How to build a screen in `apps/web` against the generated API client.

Canonical rules live in `docs/architecture.md` and
`apps/web/src/features/README.md`. This skill is the *how*.

The response envelope is not described here — it is produced by the backend
but owned by the `researchos-contract` skill. Read that skill when a response
looks wrong or when `query.data` has the wrong type.

## Folder boundaries

```text
apps/web/src/
  app/                      Next.js owns this tree
    <segment>/_components/  Only used by that segment
  components/
    ui/                     Shared primitives — know nothing about a domain
    providers/              App-wide client providers
  features/
    <domain>/               One folder per business domain
      index.ts              Barrel — the only import surface
      types.ts              Domain types the UI consumes
      hooks/                API calls and state normalisation
      components/           Domain components
  lib/
    api/                    GENERATED BY Orval — never hand-edited
    axios-instance.ts       Orval mutator — unwraps the response envelope
    api-error.ts            Helpers for reading a failed request
  theme/                    MUI theme
```

Four rules that the tooling enforces or that keep the codebase navigable:

1. **`src/lib/api/` belongs to Orval.** The config runs with `clean: true`, so
   every hand-written file there is deleted on the next codegen. The eslint
   rule `no-restricted-imports` blocks **value** imports from `@/lib/api/*`
   — import values from the `@/lib/api` barrel instead.

   The one exception is a **type-only** import, which the rule permits via
   `allowTypeImports`:

   ```typescript
   import type { ApiErrorResponseDto } from '@/lib/api/models';
   ```

   A type is erased at build time, so it cannot pull a deleted runtime
   module into the bundle — which is the actual risk the rule guards
   against. Importing a *value* from `@/lib/api/*` is still an error.

   There are two generated barrels and they export **disjoint** sets:
   `@/lib/api` holds the operations (hooks, API functions), while
   `@/lib/api/models` holds the types. Neither re-exports the other, so a
   type-only import has to name the models barrel explicitly.

   Allowed and blocked import forms: `reference.md`.

2. **`components/ui/` knows nothing about a domain.** A file there must not
   mention `Profile`, `Opportunity` or `Taxonomy`. Same principle as
   `src/common/` in the backend.
3. **Features do not import each other.** If a feature needs another
   feature's data, call that feature's hook, not its files.
4. **The feature folder name matches the backend module.**
   `features/taxonomy/` ↔ `apps/api/src/modules/taxonomy/`. This is how a
   reviewer traces a screen back to its backend module.

## The response envelope in one line

The frontend never unwraps it by hand — the Orval mutator
`src/lib/axios-instance.ts` unwraps one level, so `query.data` is the
**payload** type (`HealthStatusDto`), not the envelope.

```typescript
// Right — data is the payload.
<Typography>{query.data.status}</Typography>

// Wrong — the envelope was already unwrapped.
<Typography>{query.data.data.status}</Typography>
```

Errors are *not* unwrapped: a failed request rejects in axios, so
`error.response.data` is still the full error envelope. Read the message
through `apiErrorMessage(error)` from `src/lib/api-error.ts`, never
`String(error)`.

Full details: the `researchos-contract` skill.

## Transport → domain → UI

Three layers, and the middle one exists for a reason.

| Layer | Location | Owns |
| --- | --- | --- |
| Transport | `src/lib/api/` (Orval) | Request, cache key, query lifecycle |
| Domain | `features/<domain>/hooks/` | DTO → domain type, state normalisation |
| UI | `features/<domain>/components/`, `components/ui/` | Rendering |

The domain layer means a screen never branches on raw query flags. It reads
one explicit status.

### The `isPending` trap

`isPending` means "no data yet". For a query with `enabled: false` it is
`true` forever, so a spinner bound to it never stops and a button disabled by
it can never be clicked.

| Flag | Meaning | Use it for |
| --- | --- | --- |
| `isFetching` | A request is in flight | Disabling a submit button, "Đang tải…" labels |
| `isPending` | No data yet | Only when the query is enabled and has never resolved |
| `isSuccess` | The last attempt succeeded | Rendering data |
| `isError` | The last attempt failed | Rendering an error state |

The feature hook should hide these behind explicit names, as
`features/health/hooks/use-api-health.ts` does with `isHealthy`, `isFetching`
and `isFailed`.

## Writing a feature

A feature folder is `index.ts` (barrel), `types.ts` (domain types), `hooks/`
(API calls + state normalisation) and `components/`.

The hook is where the DTO becomes a domain type, and where raw query flags
become explicit ones. Note `enabled: Boolean(id)` — without it, a request
fires with an empty id.

```typescript
'use client';

export function useProfile(id: string) {
  const query = useProfilesControllerFindOne(id, {
    query: { enabled: Boolean(id) },
  });

  const data: Profile | undefined = query.data
    → { id: query.data.id, displayName: query.data.displayName }
    : undefined;

  return {
    ...query,
    data,
    /** The API answered and the record loaded. */
    isLoaded: query.isSuccess && data !== undefined,
    /** A request is currently in flight. */
    isFetching: query.isFetching,
    /** The last attempt failed. */
    isFailed: query.isError,
  };
}
```

The barrel is the only import surface other modules may use:

```typescript
export { useProfile } from './hooks/use-profile';
export type { Profile } from './types';
```

The component then branches on the hook's explicit flags, never on
`query.data` being undefined — an `isPending` branch renders a
`LoadingSkeleton`, an `isFailed` branch renders an `ErrorState` with a
retry, and only then does it read `data`.

Full templates for each file: `reference.md`.

## Loading states

Two different kinds of waiting, two different treatments.

| What is loading | Use |
| --- | --- |
| A block of content that will be replaced by data (list, card, detail panel) | **Skeleton** — reserves the space, prevents layout shift |
| A mutation in flight (submit, save, delete) | **Spinner in the button** — the layout does not change |

### Skeletons for block loading

A spinner hides the layout; a skeleton reserves the space and prevents a
layout shift when data arrives. Use skeletons whenever the thing being loaded
*occupies an area* of the page.

Shared primitives in `components/ui/feedback.tsx`: `LoadingSkeleton` (a
block of content — `variant` is `text`, `rectangular` or `circular`),
`ListItemSkeleton` (a row in a list) and `EmptyState` (loaded successfully,
nothing to show — **not** an error).

Match the skeleton's dimensions to the real content. A skeleton of a different
size causes the layout to jump.

### Spinners for mutations

A mutation does not change the layout — the button stays where it is and the
page keeps its content. A spinner belongs *in* the button, not in the page
body.

MUI v9's `Button` has a built-in `loading` prop that renders a
`CircularProgress` and disables the button, so a second submit cannot fire
while the first is in flight. `loadingPosition` controls where the indicator
sits — `'start'` keeps the label visible and pushes it right, `'center'`
replaces the label with the spinner.

Bind it to the **mutation's** pending flag, not a query's. `isPending` on a
query with `enabled: false` is `true` forever; a mutation that is disabled
has not fired at all, so `isPending` on it is the correct signal.

```typescript
// Wrong — query.isPending can be true forever on a disabled query.
<Button loading={query.isPending}>Lưu</Button>

// Right — a mutation is either fired or not.
<Button loading={mutation.isPending}>Lưu</Button>
```

The full-page spinner still has no place: a screen waiting for its first
block of data shows a skeleton, not a spinner.

## Mutation feedback

**Every mutation gives feedback.** A user who clicks a button and sees
nothing happen cannot tell whether the click registered. This is not
optional, and it applies to both outcomes.

| Outcome | Feedback |
| --- | --- |
| Success | A confirmation — the user knows it worked |
| Error | The server's message, shown where the user is looking |

### The rule

- **Success → snackbar.** The page is already correct at this point. A toast
  confirms and gets out of the way.
- **Error → inline, next to the thing that failed.** A toast is transient and
  disappears; an error that vanishes is an error the user will hit again.
  Put it where the user has to look — under the field, in the panel, in the
  form.

This is the asymmetry that matters: **success is a notification, failure is
a state.** A form that failed validation shows the errors under the inputs
and keeps the user on the page. A form that succeeded says so and moves on.

```typescript
// Success — transient, confirms, dismisses itself.
showSnackbar({ severity: 'success', message: 'Đã lưu hồ sơ.' });

// Error — persistent, next to what failed, with a way forward.
<ErrorState
  title="Không lưu được hồ sơ"
  message={apiErrorMessage(mutation.error)}
  onRetry={() => void mutation.mutate(payload)}
/>
```

### Why not a snackbar for errors

A snackbar is a notification channel, not a state channel. It auto-hides, so
an error the user did not read in four seconds is an error they will repeat;
it is spatially detached from the cause, so an error under a field points at
the field while a toast in the corner points at nothing; and it cannot hold
per-field validation messages legibly. The backend groups those by field —
`apiFieldErrors(error)` returns them — and a form needs one message under
each input.

The exception: an error with no local anchor — a background sync, a bulk
action, a failed logout — has nowhere to render inline. Then a snackbar with
`autoHideDuration: null` and a retry action is the right call.

Validation errors are inline, always: a `400` carries `errors` grouped by
field, so render each message under its input with `apiFieldErrors(error)`.
Never collapse them into one toast line. Wiring, snackbar props and the
Strict Mode pitfall: `reference.md`.

## Error states

### In a component

Use `ErrorState` from `components/ui/feedback.tsx`. Every error state offers a
way forward — a dead-end message with no recovery action is a bug.

```typescript
<ErrorState
  title="Không tải được hồ sơ"
  message="Máy chủ không phản hồi. Thử lại sau."
  onRetry={() => void refetch()}
/>
```

### At component level

`components/ui/error-boundary.tsx` wraps `catchError` from `next/error`. Use
it when one widget can fail without taking the page down.

```typescript
<ErrorBoundary title="Lỗi ở cấp component">
  <SomeWidget />
</ErrorBoundary>
```

`catchError` is preferred over a hand-rolled React error boundary class: it
re-renders inside a Transition so surrounding client state survives, it lets
`redirect()` and `notFound()` pass through instead of swallowing them, and it
clears the error on client navigation.

### At route level

Next.js file conventions:

| File | Catches |
| --- | --- |
| `app/error.tsx` | Uncaught errors in that segment and its children. Props: `error`, `retry()` |
| `app/global-error.tsx` | Failure in the root layout. Renders its own `<html>` and `<body>` |
| `app/loading.tsx` | Suspense fallback while the segment resolves |
| `app/not-found.tsx` | `notFound()` |
| `app/unauthorized.tsx` | `unauthorized()` — needs `experimental.authInterrupts` |
| `app/forbidden.tsx` | `forbidden()` — needs `experimental.authInterrupts` |

Scope an `error.tsx` to the narrowest segment that owns the failure. A crash
in one feature should not take down the whole app.

`notFound()`, `unauthorized()` and `forbidden()` work by throwing during a
server render, so they cannot be called from a click handler. Give each one a
dedicated route that calls it. The backend enforces permission; the frontend
only reflects it — the route decides, the boundary renders.

In `error.tsx`, `error` is typed `unknown` — narrow it with `instanceof Error`
before reading `.message`. Do not name the component `Error`: a default export
named `Error` shadows the global constructor and breaks `instanceof` checks
inside that module.

Next.js 16.4 passes both `reset` and `retry` to an error boundary. `retry`
re-renders the failed segment and is what a "try again" button should call;
`reset` clears the boundary state. `app/error.tsx` uses `retry`.

Route templates and the access-boundary routes: `reference.md`.

## MUI and Tailwind

### v9 prop surface

MUI v9 removed the system props from the direct prop surface. `gap`, `flex`,
`py`, `px`, `alignItems`, `textAlign` and `fontWeight` must go through `sx`,
or they leak onto the DOM as invalid HTML attributes.

```typescript
// Wrong — leaks to the DOM
<Stack alignItems="center" gap={2} textAlign="center">
  <Typography fontWeight={500}>Tiêu đề</Typography>
</Stack>

// Right
<Stack spacing={2} sx={{ alignItems: 'center', textAlign: 'center' }}>
  <Typography sx={{ fontWeight: 500 }}>Tiêu đề</Typography>
</Stack>
```

`spacing` on `Stack` still works as a prop. `align` on `Typography` still works
as a prop — it is not the same as `textAlign`.

### Links

Next.js 16 refuses to pass a function from a Server Component to a Client
Component, so `<Button component={Link}>` fails. Use the client wrapper:

```typescript
import NextLink from '@/components/ui/link';

<Button component={NextLink} href="/profiles">Hồ sơ</Button>
```

### Cascade

`globals.css` declares:

```css
@layer theme, base, mui, components, utilities;
```

`mui` sits below `utilities`, so a Tailwind utility class beats a MUI
component's own styles without `!important`. This only works while
`layout.tsx` mounts `AppRouterCacheProvider` with `enableCssLayer: true`.
Changing either one silently breaks the cascade.

## Responsiveness

A component renders correctly at every width, without a JavaScript branch.
`components/ui/header.tsx` and `components/ui/search-bar.tsx` are the
reference implementations — copy their shape.

### Breakpoints

MUI's defaults, in px: `xs` 0, `sm` 600, `md` 900, `lg` 1200, `xl` 1536.
`xs` is a phone; `md` is where the inline nav and search field appear.

**Tailwind's breakpoints differ**: `sm` 640, `md` 768, `lg` 1024, `xl` 1280,
`2xl` 1536. MUI `md` is 900, Tailwind `md:` is 768 — they are not the same
line. Use one system per component; never mix `sx={{ display: { md: 'none' } }}`
with a `md:hidden` class in the same tree.

### Swap with `sx`, do not measure

```typescript
// Wrong — a JS branch renders a different tree on the server and the client.
const isDesktop = useMediaQuery('(min-width:900px)');
return isDesktop → <DesktopNav /> : <MobileNav />;

// Right — one tree, CSS decides.
<Box sx={{ display: { xs: 'none', md: 'flex' } }}>
  <DesktopNav />
</Box>
```

`useMediaQuery` is for *behaviour* differences (a different chart, a media
element), not layout. Its server value is `false`, so the server renders the
mobile branch; if the difference matters for markup, gate it on mount.

### Collapse to a menu, keep one trigger

The nav links and the search field use the same four-part shape:

1. An `IconButton` trigger with `aria-label`, `aria-controls` and
   `aria-haspopup`, shown only below the breakpoint.
2. A `Menu` anchored to it with `keepMounted` and `disableAutoFocusItem`.
3. The menu's own `sx={{ display: { xs: 'block', md: 'none' } }}` — a
   kept-mounted popup must be hidden on wide screens, or it lingers in the
   DOM and can flash on resize.
4. The inline version, hidden on small screens.

The menu's content is the same component that the inline version renders —
one source of truth, two presentations.

### Never let a child overflow

A flex child that holds text needs `minWidth: 0`, or it refuses to shrink and
pushes the row wider than the viewport. Truncating labels use `noWrap` plus
`overflow: 'hidden'` and `textOverflow: 'ellipsis'`. A popover width is
`min(92vw, 420px)` — a fixed `420px` overflows a phone.

Details, templates and the breakpoint table: `reference.md`.

## Dark mode

`components/providers/theme-provider.tsx` bridges next-themes to MUI:
next-themes owns the preference and writes the `class` on `<html>`, and the
sync calls MUI's `setMode` so both agree.

Read the theme only after mount. next-themes cannot know the resolved theme
during SSR — it depends on the client preference and the OS setting — so
reading it during render makes the server and client produce different markup
and triggers a hydration mismatch. Use `useSyncExternalStore` for
browser-only state, with a different server snapshot.

## Verifying

```powershell
pnpm --filter web lint
pnpm --filter web build
pnpm build && pnpm lint && pnpm test
```

Check the change in a browser, not just the build. A build passing does not
prove the loading state appears, the error state recovers, or the cascade
resolves in the right order.

`/demo` is a scratch page that exercises these conventions end to end — MUI
components, the cascade, dark mode, the API client, loading, error and the
access boundaries. Use it to confirm a change behaves.

If the change adds or changes an endpoint, regenerate the client first — see
the `researchos-api-endpoint` skill for the codegen step.

## Checklist

- [ ] Feature folder named after the backend module
- [ ] `index.ts` barrel is the only import surface
- [ ] Domain types in `types.ts`, derived from the generated models
- [ ] Domain hook normalises state; the UI branches on explicit flags
- [ ] `isFetching` for in-flight, `isPending` only for never-resolved enabled queries
- [ ] No hand-written file under `src/lib/api/`
- [ ] No manual unwrapping of the envelope — `query.data` is already the payload
- [ ] Error messages read through `apiErrorMessage()`, never `String(error)`
- [ ] Loading uses skeletons sized like the real content
- [ ] Mutations show a spinner in the button or where applicable, not a page spinner
- [ ] Every mutation has a success feedback (snackbar) and an error feedback (inline)
- [ ] Validation errors are rendered per field, not flattened
- [ ] Every error state offers a retry or another way forward
- [ ] Route errors handled by the narrowest `error.tsx`
- [ ] Localization, refer to the localization skill
- [ ] MUI layout props passed through `sx`; links use the `components/ui/link` wrapper
- [ ] Responsive layout uses `sx` breakpoints, not a `useMediaQuery` branch
- [ ] Collapsed menus hide themselves on wide screens (`display` on the `Menu`)
- [ ] Flex children that hold text set `minWidth: 0`; popovers use `min(92vw, …)`
- [ ] `pnpm build`, `pnpm lint`, `pnpm test` pass
