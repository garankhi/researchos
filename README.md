# ResearchOS

Monorepo pnpm gồm Next.js (web), NestJS (API) và NestJS (worker), dùng
PostgreSQL và Prisma.

> **Đọc `ResearchOS.sql` trước khi đụng database.** Trong workspace này, file SQL
> đó là nguồn sự thật duy nhất của schema. `packages/database/prisma/schema.prisma`
> là **artefact được sinh ra**, không sửa tay. Chi tiết ở
> [docs/database.md](./docs/database.md).

## Cấu trúc

```text
apps/
  web/         Next.js App Router
  api/         NestJS HTTP API
  worker/      NestJS background worker
packages/
  config/      Cách tìm và nạp file .env dùng chung
  database/    Prisma client dùng chung API/worker (schema do ResearchOS.sql sinh ra)
ResearchOS.sql         Nguồn sự thật của schema PostgreSQL
docker-compose.yml     PostgreSQL + Redis cho local
docs/
  architecture.md    Kiến trúc tổng thể
  api-convention.md  Quy ước tạo API
  database.md        Thiết lập database và Prisma
  scaffolding.md     Hướng dẫn tạo scaffold
  workspace.md       pnpm workspace và Turborepo
```

## Khởi tạo

```powershell
pnpm install
Copy-Item .env.example .env
docker compose up -d
pnpm db:reset
pnpm dev
```

Từng bước:

1. **`pnpm install`** — cài dependency toàn workspace.

2. **`Copy-Item .env.example .env`** — tạo file biến môi trường ở root. Giá trị
   mặc định đã khớp với `docker-compose.yml`:

   ```dotenv
   DATABASE_URL="postgresql://postgres:postgres@localhost:5433/researchos?schema=public"
   REDIS_URL="redis://localhost:6379"
   ```

   Cổng **5433** vì máy Windows thường đã có PostgreSQL native chiếm 5432;
   container giữ 5432 bên trong và publish ra 5433.

3. **`docker compose up -d`** — bật PostgreSQL và Redis. Kiểm tra bằng
   `docker compose ps`, cả hai service phải báo `healthy`.

4. **`pnpm db:reset`** — drop database, tạo lại, apply `ResearchOS.sql`, rồi
   introspect lại để sinh `schema.prisma` và Prisma client. **Lệnh này xoá toàn
   bộ dữ liệu.**

5. **`pnpm dev`** — chạy web và API.

Sau đó:

| URL | Là gì |
| --- | --- |
| http://localhost:3000 | Web |
| http://localhost:4000 | API |
| http://localhost:4000/docs | Swagger UI |
| http://localhost:4000/health/ready | Kiểm tra API đã kết nối database |

Kiểm tra database đã sẵn sàng:

```powershell
Invoke-WebRequest 'http://localhost:4000/health/ready' | Select-Object -ExpandProperty Content
```

Kết quả mong đợi là `"status":"ok"`. Nếu là `"degraded"`, xem
[docs/database.md §10](./docs/database.md).

## Đổi schema

```powershell
# 1. Sửa ResearchOS.sql
# 2. Dựng lại database + datamodel
pnpm db:reset
# 3. Xác nhận datamodel khớp SQL
pnpm db:drift
```

Nếu thay đổi SQL không đòi hỏi đổi datamodel (thêm `CHECK`, thêm comment, đổi
một `VIEW`), `db:drift` vẫn báo "No drift" — điều đó đúng.

## Prisma ở đây hoạt động khác thường

Prisma trong workspace này là **ORM client có kiểu**, **không phải** chủ sở hữu
schema. Nói cách khác: bạn vẫn dùng `prisma.user.findUnique(...)` bình thường,
nhưng Prisma **không tạo ra bất kỳ DDL nào** và **không có migration nào**.

Lý do: schema hiện có 47 `CHECK` constraint, 91 foreign key `DEFERRABLE`, 2
expression index, 3 partial unique index, 2 view và 1 trigger — tất cả đều là
thứ ngôn ngữ schema của Prisma **không biểu diễn được**. Đã kiểm chứng bằng
thực nghiệm trên Prisma 7.10.1: một migration do Prisma sinh ra đối chiếu với
`ResearchOS.sql` **mất sạch** những object đó.

Những điều này sẽ gây bất ngờ nếu bạn không biết:

| Điều | Vì sao lạ |
| --- | --- |
| `schema.prisma` có header `DO NOT EDIT THIS FILE BY HAND` | Nó được sinh ra từ database đang chạy rồi viết lại theo quy ước repo (PascalCase model, camelCase field, `@map`/`@@map`). Sửa tay thì `db:drift` báo lỗi. |
| Không có `prisma migrate` nào | `prisma.config.ts` không có block `migrations`, cũng không có `shadowDatabaseUrl`. Script `db:migrate`, `db:migrate:deploy`, `db:status` đã bị gỡ khỏi toàn bộ workspace. |
| `db:drift` không dùng `prisma migrate diff` | Differ của Prisma 7 **mù** với `CHECK`, view và trigger: xoá hẳn một CHECK constraint khỏi database rồi diff lại, nó vẫn báo "empty migration". Một check không bao giờ đỏ thì không mang thông tin gì. `db:drift` so **introspection với introspection**: dựng database tạm từ SQL, introspect, cùng một transform, rồi so với file đã commit. |
| View không có model trong Prisma | `effective_user_access` và `released_output_versions` không truy cập được qua client. Dùng `$queryRaw` với SQL viết tay. |
| Một số field bị trigger chi phối | `opportunity_applications.applied_at` và `response_due_at` được trigger ghi đè lúc insert. `create()` trả về giá trị **đã đúng**, không cần re-read. |
| `response_due_at` bắt buộc, không có default | Không có trigger thì bảng `opportunity_applications` không insert được. |
| Lỗi constraint trước đây trả 500 | `PrismaClientKnownRequestError` không phải `HttpException`, nên filter cũ trả 500 kèm SQL thô. **Đã sửa** — xem bên dưới. |
| `PrismaClient` cần driver adapter | Prisma 7 bắt buộc: `new PrismaClient({ adapter: new PrismaPg({ connectionString }) })`. `PrismaService` đã làm sẵn. |
| Enum import từ `@researchos/database` | Không import trực tiếp từ `packages/database/src/generated/...` — đường dẫn generated là chi tiết nội bộ của package. |

### Lỗi từ database giờ trả 400/409, không còn 500

`apps/api/src/common/filters/database-error.ts` đọc Postgres error code trong
`error.meta.driverAdapterError.cause.originalCode` và map:

| Postgres code | Ý nghĩa | HTTP status |
| --- | --- | --- |
| `23514` | Vi phạm `CHECK` constraint, hoặc lỗi do trigger ném | 400 |
| `23503` | Vi phạm foreign key | 400 |
| `23505` | Vi phạm unique constraint | 409 |
| `23502` | `NOT NULL` bị vi phạm | 400 |

Mã Prisma cũng được map: `P2002` → 409, `P2003` → 400, `P2014` → 400,
`P2025` → 404, `P2034` → 409.

`message` thô của Prisma **không bao giờ** được gửi cho client, vì nó chứa tên
bảng, tên constraint và cả nội dung dòng dữ liệu (`Failing row contains (...)`).
Message do PostgreSQL sinh ra bị thay bằng message chung; message do trigger viết
(ví dụ `opportunity ... is not open (status is DRAFT)`) thì được giữ lại, chỉ
UUID được thay bằng `<id>`.

Chi tiết đầy đủ vẫn vào log server: `warn` cho lỗi 4xx, `error` kèm stack cho
lỗi 5xx.

### Hệ quả: không có rollback

Vì không có migration history, cách triển khai là apply `ResearchOS.sql` lên
database production rồi khởi động app version mới. Điều này đòi hỏi migration
**tương thích ngược**: app version cũ vẫn phải chạy được với schema mới. Xem
[docs/database.md §5.4](./docs/database.md).
